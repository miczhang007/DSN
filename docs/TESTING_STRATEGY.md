# 自动化测试策略

## 目标与原则

- 本地 SQLite 是离线工作的真实数据源；任何联网故障都不能阻塞本地读写。
- 测试数据必须是合成数据；不得提交 Token、密码、数据库连接串或真实用户数据。
- 前端测试必须 Mock Tauri `invoke`；Rust 测试必须使用内存 SQLite。禁止测试访问真实用户数据库。
- 不以打包结果代替测试。

## 测试分层

| 类型 | 目的 | 适用时机 | 入口 |
| --- | --- | --- | --- |
| 前端主场景 | 还原稳定核心用户路径，防止改动破坏既有能力 | 每次改前端代码后；打包前 | `npm run test:main` |
| Rust 单元测试 | 锁定后端纯逻辑与数据库约束（校验、迁移、周期规则、单实例） | 每次改 `src-tauri/src/lib.rs` 后 | `npm run test:rust` |
| 全量回归 | 以上两者的组合 | 发布前、远端更新前 | `npm run test:all` |
| 监听模式 | 开发期增量反馈 | 开发过程中 | `npm run test:watch` |

`npm test` 等价于 `npm run test:main`（保持既有 CI 与脚本兼容）。

## 当前用例归属

### 前端（Vitest + jsdom）

- `tests/App.spec.js`：进入应用、用户管理、任务创建/详情/节点/进度、历史撤销、周期规则、错误提示、生命周期展示等核心交互。
- `tests/recurring-task-change.spec.js`：周期任务相关的一次性变更回归。
- `tests/datetime.spec.js`、`tests/labels.spec.js`：日期换算、状态与事件文案等纯函数。
- `tests/errors.spec.js`：错误文案提取与全局错误兜底（含 Vue 异步事件处理器异常的捕获路径）。

### Rust（`cargo test --lib`）

- `src-tauri/src/lib.rs` 的 `local_hardening_tests` 模块，覆盖：
  - 外链白名单：只放行 http/https，拒绝 `javascript:`、`file:` 与参数注入；
  - 数据库连接：`journal_mode=WAL`、`foreign_keys=ON` 实际生效；
  - 单实例：同一互斥量第二次获取失败，释放后可再次获取（仅 Windows）；
  - 周期规则：按日/按周/日期范围的适用判定；
  - 跨日归档依赖的「ISO 日期字典序等于时间序」不变量；
  - 周期任务补齐的幂等性（重复刷新不重复生成）。

## 执行策略

### 代码变更后

1. 根据改动文件和调用链识别受影响范围。
2. 前端变更新增/更新 `tests/*.spec.js`；后端变更在 `local_hardening_tests` 或新模块中补用例。
3. 运行对应入口：只改前端跑 `npm run test:main`，只改 Rust 跑 `npm run test:rust`，两边都改跑 `npm run test:all`。
4. 未通过时调整实现或用例并重复执行；无法消除阻塞时，报告测试结果与原因。
5. 执行结束后在对话中列出实际执行的用例与通过/失败状态，不只给通过数量。

### 打包、发布、远端更新前

1. 执行 `npm run test:all`。
2. 通过后才能继续用户已授权的打包、发布或远端更新操作。
3. 不通过时停止上述操作，报告失败用例、错误信息和影响范围，不得绕过。

## 编写原则

1. 变更测试与被长期稳定下来的主场景用例分开维护，避免主场景文件变成大杂烩。
2. 新增测试命令时必须同步纳入 `test:all`，避免全量验证遗漏新入口。
3. 云同步、账号等后续功能遵循同一分层，并在私有云服务项目中分别维护接口契约、服务端单元测试和端到端测试。
