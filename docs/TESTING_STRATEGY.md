# 自动化测试策略

## 测试分层

自动化测试按职能拆分，避免每次开发都把所有测试当作本次变更测试执行。

| 类型 | 目的 | 适用时机 | 当前入口 |
| --- | --- | --- | --- |
| 本次变更测试 | 验证本次需求、修复及其边界条件；用例随本次改动增补 | 每次代码变更完成后 | 对应 `npm run test:change:*` |
| 主场景回归测试 | 还原稳定核心用户路径，防止改动破坏既有能力 | 打包、发布、远端更新前 | `npm run test:main` |
| 全量回归测试 | 组合执行以上两类测试 | 发布前或需要完整验证时 | `npm test` 或 `npm run test:all` |

## 当前用例归属

### 本次变更回归：周期任务

- `tests/recurring-task-change.spec.js`：新增按日规则默认勾选全部日期，并正确提交日期集合。
- `src-tauri/src/lib.rs` 中的 Rust 单元测试：按日指定日期匹配、按日空日期不生成、当日自动创建、按周多次串行创建、过期自动归档。

### 通用主场景还原

主场景回归由两层共同组成，执行 `npm run test:main`：

- Web：`tests/App.spec.js` 验证用户进入应用、创建普通任务、进入详情维护任务/进度/节点，以及生命周期日志展示等关键用户入口与界面反馈。
- Rust：`src-tauri/src/lib.rs` 的 `main_scenario_tests` 使用内存 SQLite 还原真实数据链路，覆盖普通任务的创建—节点/进度—完成归档、历史任务撤销完成与逻辑删除、周期规则创建—自动生成—作废阻止后续生成。

主场景测试的目标是还原业务闭环与数据结果，不以单个按钮、菜单开合等局部交互替代主流程验证；局部交互和缺陷边界应归入本次变更测试。

## 执行策略

### 代码变更后：本次变更测试

1. Agent 根据需求、改动文件和调用链识别受影响范围。
2. 在 `tests/<feature>-change.spec.js` 或对应 Rust 测试模块中新增、更新本次变更测试；仅覆盖本次功能、修复和必要边界。
3. 执行对应 `npm run test:change:<feature>`。
4. 未通过时，调整实现或测试用例并重复执行，直至通过；无法消除阻塞时，报告测试结果与原因。
5. 每次执行结束后，在对话中逐条列出实际执行用例的名称和通过、失败或跳过状态；失败项附简要错误原因，不得仅给出通过数量。

### 打包、发布、远端更新前：主场景回归测试

1. Agent 评估本次改动是否会影响稳定核心用户路径，并在需要时更新 `tests/App.spec.js` 或后续独立的主场景测试文件。
2. 执行 `npm run test:main`。
3. 测试通过后，才能继续用户已授权的打包、发布或远端更新操作。
4. 测试不通过时，停止上述操作，报告失败用例、错误信息和影响范围；不得绕过失败继续执行。
5. 无论通过或失败，均须在对话中逐条报告本次实际执行的主场景用例状态。

### 全量验证

- `npm test` / `npm run test:all` 用于发布前的完整验证，依次执行主场景回归及已纳入脚本的变更测试。
- 新增 `test:change:*` 命令时，必须同步纳入 `test:all`，避免全量测试遗漏新功能。

## 编写原则

1. 本次变更测试不直接混入主场景回归测试；已经长期稳定且代表核心用户流程的用例，才沉淀为主场景用例。
2. 前端测试必须 Mock Tauri `invoke`；后端测试必须使用内存 SQLite。禁止测试访问真实用户数据库。
3. 云同步、账号等后续功能遵循同一分层，并在私有云服务项目中分别维护接口契约、服务端单元测试和端到端测试。
